# FINDINGS — first evidence pass, 2026-08-03

Six findings from the first primary-source research pass. Each is traceable to
captured Class A evidence. Three of them **invalidate a comparison that is
standard practice across this entire ecosystem**, which is the strongest early
argument that the Atlas is worth building.

---

## F1 — Per-token price is not comparable across tokenizers

**Evidence:** `src-anthropic-pricing-2026-08-03` excerpt 5;
`src-anthropic-models-overview-2026-08-03` excerpt 3. Both verbatim, Class A.

> "This tokenizer produces approximately 30% more tokens for the same text. The
> exact increase depends on the content and workload shape."

Anthropic documents that models from Claude 4.7 onward use a tokenizer producing
**~30% more tokens for identical text** than earlier models.

**Consequence.** Every price-per-million-token comparison in this ecosystem
implicitly assumes tokens are a common unit. They are not — not across model
generations from one vendor, and certainly not across vendors, who have never
shared tokenizers. A model priced 10% cheaper per token can be *more* expensive
per unit of actual work.

The Atlas already anticipated this structurally: `met-effective-token-multiplier`
exists in `obj-cost-efficiency` precisely to normalize it. This finding
promotes it from a design precaution to a measured requirement.

**What we cannot yet say:** the multiplier for any *cross-vendor* pair. Nobody
publishes it. It requires tokenizing a fixed corpus with each vendor's tokenizer
and comparing counts — a small, cheap, high-value experiment that no one appears
to have run publicly. **Proposed as `exp-tokenizer-normalization-v1`, and it is
the highest value-per-effort experiment currently identified.**

**Unresolved (RG-001):** whether Claude Sonnet 5 uses the newer tokenizer. The
pricing page says "Claude 4.7 and later models"; the models overview attaches the
tooltip explicitly to Fable 5 and names "Sonnet 4.6 and earlier" as using the old
one. Sonnet 5 is not named either way. Recorded as a `conflicts` block with
`likely_cause: unexplained` rather than resolved by inference.

## F2 — The most capable model has the tightest throughput ceiling

**Evidence:** `src-anthropic-rate-limits-2026-08-03` excerpts 1–3. Verbatim, Class A.

| Tier | Claude Fable 5 ITPM | Claude Opus 5 / Sonnet 5 ITPM | Ratio |
|---|---|---|---|
| Start | 500,000 | 2,000,000 | **4.0×** |
| Build | 1,500,000 | 5,000,000 | **3.3×** |
| Scale | 4,000,000 | 10,000,000 | **2.5×** |

Output limits follow the same shape (Start: 100k vs 400k OTPM).

**Consequence.** Anthropic's most capable widely-released model is also its most
rate-constrained — by a factor of 2.5–4× against its own stablemates at every
tier. For sustained or parallel agentic work, **the binding constraint may be
throughput rather than price or quality.** A stack that looks affordable can
still be infeasible.

This is exactly the class of fact that decides real adoptions and appears in no
benchmark, no leaderboard, and no comparison article. It is a specification fact,
freely published, and simply never collected alongside the quality claims it
contradicts.

**Note also:** Opus 4.x models share a *combined* rate-limit bucket, while Opus 5
has its own. Migrating from 4.x to 5 therefore changes your effective throughput
independently of any change in the model itself.

## F3 — Prompt caching is a throughput lever, not only a cost lever

**Evidence:** `src-anthropic-rate-limits-2026-08-03` excerpts 4–5. Verbatim, Class A.

> "With a 2,000,000 ITPM limit and an 80% cache hit rate, you could effectively
> process 10,000,000 total input tokens per minute (2M uncached + 8M cached),
> because cached tokens don't count toward your rate limit."

Cache reads are excluded from ITPM for most Claude models. Caching therefore
multiplies effective throughput by roughly `1/(1−hit_rate)` **in addition to**
reducing cost to 0.1× base input.

**Consequence for the cost model.** `cache_hit_rate` in a usage profile is now
established as load-bearing on two axes simultaneously — cost *and* feasibility.
It was already the assumption we flagged as most uncertain. This raises its
value-of-information rank further: getting it wrong misprices a stack *and*
misjudges whether the stack can run at all.

It also means a harness that caches well and a harness that does not are not
minor variants of the same stack. They are different products at the same price.

## F4 — A dated price cliff, 28 days out

**Evidence:** `src-anthropic-pricing-2026-08-03` excerpts 0–1. Verbatim, Class A.

Claude Sonnet 5 introductory pricing ($2/$10 per MTok) ends **2026-08-31**;
standard pricing ($3/$15) begins 2026-09-01. A **50% increase on both sides**.

**Consequence.** Any cost analysis published today that does not carry a validity
interval is wrong within a month. This is precisely the failure the bitemporal
model was built to prevent: the Atlas stores two facts with adjacent intervals,
so "what does this cost?" resolves correctly *at any reference date*, and the
September figure is already in the graph rather than arriving as a correction.

Scheduled re-verification is set for 2026-09-01 as a dated event, not a
discretionary review.

## F5 — Pricing *shapes* are not commensurable, before prices even matter

Three vendors, three structurally different billing models observed in one pass:

| | Anthropic | OpenAI | Google |
|---|---|---|---|
| Cache pricing | Multiplier on base (1.25× / 2× write, 0.1× read) | Flat cached-input rate | Per-token rate **plus $1.00/1M tokens per hour storage** |
| Speed tiers | Fast mode at 2× (Opus only) | — | standard / batch / flex / **priority** |
| Geography | 1.1× for US-only | 10% uplift, models after 2026-03-05 | not captured |
| Batch | −50% | −50% | −50% |

**Consequence.** Google bills cache **storage by time**, which is a cost that
accrues while you are doing nothing. Anthropic bills cache as a multiplier on
writes with time-limited validity. These are not the same product with different
numbers; they have different failure modes — one punishes idle sessions, the
other punishes cache misses.

A cost model with a single "cache discount" field cannot represent both. The
schema's per-component cost function (RECOMMENDATION §6) must gain a
time-based storage term. **Logged as RG-004; this is a real gap in the cost
model, found by data rather than by reasoning.**

## F6 — A vendor's own API surface corroborates the endpoint distinction

**Evidence:** `src-openrouter-provider-routing-2026-08-03` excerpt 3.
Reduced fidelity — corroborating only.

OpenRouter exposes a `quantizations` parameter filtering upstream providers by
quantization level (int4, int8, fp8), and a `data_collection` policy filter
defaulting to `"allow"`.

**Consequence.** The existence of a quantization *filter* is direct evidence that
**the same nominal model is served at different quantizations by different
providers** — which is the `model_endpoint` distinction (TAXONOMY §2 L1) showing
up in a production API surface. A measurement attached to "the model" rather than
to the endpoint is therefore under-specified in practice, not just in theory.

Two further observations, both needing verbatim confirmation:
- The default routing objective is **price**, weighted inverse-square. Absent
  explicit configuration, a router optimizes for *its* cheapest path, which is
  not necessarily the user's best path.
- `data_collection` defaults to `"allow"`. If confirmed, a privacy-conscious user
  must opt out explicitly — a default worth surfacing prominently.

additive extension to the cost function — a new term, not a redesign — which is
the behaviour the schema was built for.

## Method note

This pass ran the negative-case discipline only partially. Searches targeted
first-party documentation, which is systematically complete about capability and
systematically quiet about limitation. **No Class B or Class C evidence was
captured at all**, which means every finding above is a specification finding.
None of them tell you whether anything is *good*. That gap is the subject of the
next pass, and it is the reason no dimension has been scored.
