## BLOCKER 1 — RQ-08a: are subscription allowances published anywhere?

### Result

**The negative result STANDS, and is now substantially stronger.**

We retrieved the usage-limits documentation that M4 flagged as unsearched. It
does not contain absolute allowances, and it reveals *why*.

Verbatim (`support.claude.com/en/articles/9797557`, Class A, tool_extracted):

> "The number of messages you can send will vary based on your Claude plan."

> "**Current session:** How much of your plan's five-hour session limit you've
> used thus far, plus the amount of time remaining in the session."

The article states limits are affected by message length, file size, and model
choice, and directs readers to per-plan articles. We followed that chain to the
Pro/Max Claude Code article, which states limits are "shared across Claude and
Claude Code" and that `/status` shows "remaining allocation" — **again without a
single absolute number.**

### Why this strengthens rather than weakens the standard

M4 concluded the comparison was not computable from the *pricing page*, and
flagged that as a scoping weakness. Having now followed the documentation chain
two levels deeper, we can say something stronger and more specific:

**The subscription meter is not denominated in tokens at all.** It is denominated
in *five-hour sessions* and *weekly limits*, with consumption varying by message
length, attachment size, and model selected. There is no fixed token allowance
to publish, because the quantity being metered is not a token count.

This changes the character of the finding. It is not that the vendor withholds a
number — it is that **the subscription and metered products are measured in
incommensurable units**, and a crossover between them cannot exist in closed
form. Any published "X messages/month" figure would itself be an estimate under
assumptions about message size and model mix.

### Deliverables

| | |
|---|---|
| **Recommendation impact** | Q1 (`$20/month`) answer is now stronger: not merely *undisclosed* but *not denominated in a comparable unit*. The Atlas can explain **why** no source can honestly give a crossover. |
| **Schema impact** | S3 implemented; `allowanceDisclosure` enum adds `relative_only` alongside `not_publicly_disclosed`, since this case is specifically "relative multipliers over a session-based meter". |
| **Engine impact** | `NOT_PUBLICLY_COMPUTABLE` confirmed as the correct refusal code. Adds a required explanation string distinguishing *undisclosed* from *incommensurable*. |
| **New RQs** | **RQ-08e** — measure a subscription empirically to its limit under instrumentation; the only path to an absolute number. **RQ-08f** — do other vendors meter subscriptions in tokens? A vendor that does becomes the computable case. |
| **Prior conclusions** | **VALID and strengthened.** M4's RQ-08 negative result holds; its stated scoping weakness (§9) is now closed. |

## BLOCKER 2 — RQ-08b: the 200k vs 1M context discrepancy

### Result

**⛔ The discrepancy was NOT REAL. My M4 flag was wrong, and the error was ours.**

Verbatim (`support.claude.com/en/articles/8606394`, Class A, tool_extracted):

> "Claude Opus 5 and Sonnet 5 support a 1M token context window on all paid plans
> when chatting with Claude."

> "Claude Opus 4.8, Opus 4.7, Opus 4.6, and Sonnet 4.6 support a 500K token
> context window on all paid plans when chatting with Claude."

> "Outside of these models, Claude's context window size is 200K."

### Classification

Against the taxonomy the milestone specified: it is **model-specific**, with a
contributing **documentation-ambiguity** and an **extraction artifact on our
side**.

Context window is a function of **model** (and surface), not of subscription
tier. Opus 5 and Sonnet 5 provide the full 1M on paid plans — identical to the
API. The 200K figure applies to *other* models. Our M4 capture of the pricing
page was `tool_extracted`, and the extraction attached a 200K figure to a model
list it did not belong to.

**Corrected: subscription tiers are not context-degraded for current models.**

### A genuine finding uncovered while disproving the false one

The same article states that for Claude Code, "Claude Sonnet 5, **Fable 5**,
Opus 5, Opus 4.8, Opus 4.7, and Opus 4.6 support a 1M token context window."

**Fable 5 appears in the Claude Code list but not in the chat list.** If that
distinction is real rather than an omission, context window is **surface-specific
as well as model-specific** — the same model would offer different limits in chat
versus in the coding tool. Recorded as an open question, not a claim.

### Deliverables

| | |
|---|---|
| **Recommendation impact** | E5 from M4 (**"subscription and API may not share a price column"**) is **withdrawn** — its premise was false. Subscription/API remain non-comparable for the RQ-08a reason (incommensurable units), not for a context reason. |
| **Schema impact** | None. Context claims are already model-scoped; the model handled this correctly. The error was in capture, not structure. |
| **Engine impact** | Withdraw E5. No new constraint. |
| **New RQs** | **RQ-08g** — is Fable 5's chat context genuinely lower than its Claude Code context, i.e. is context surface-specific? |
| **Prior conclusions** | **INVALIDATED.** M4's flagged discrepancy was an artifact of reduced-fidelity capture. |

### What this says about our method

The M4 report labelled this an "unverified lead, not a claim" and required
verbatim confirmation before publication. **That guard worked exactly as
designed.** Had it been published as a finding, we would now be issuing a
correction to readers instead of a note to ourselves. The cost of the
`excerpt_fidelity` discipline was one extra fetch; the benefit was not being
wrong in public.

## BLOCKER 4 — RQ-01a: the first normalized cross-vendor comparison

### Result — ✅ **ACHIEVED**, and it produces a null result that corrects M4

We captured pricing for models whose exact tokenizers are publicly available
(DeepInfra, Class A, tool_extracted) and ran `exp-normalized-cost-v1`.

**This is a new study, not an amendment to RQ-01.** Its candidate list is fixed
by *which models we have pricing for*, not chosen after seeing RQ-01's results.
Only **exact** model↔tokenizer matches were admitted, because RQ-01's own H3
finding forbids substituting tokenizers across a vendor's generations.

**Four vendors, five content strata, normalized cost per identical work:**

| Model | Price in $/MTok | Tokens (py) | Cost per pass | Match |
|---|---|---|---|---|
| mistral/Mistral-Nemo-Instruct-2407 | 0.019 | 553 | $0.0000105 | exact |
| qwen/Qwen3-32B | 0.08 | 523 | $0.0000418 | exact |
| deepseek/DeepSeek-V3 | 0.32 | 541 | $0.000173 | exact |
| openai/gpt-5.6-terra | 2.00 | 507 | $0.001014 | **assumed encoding** |
| openai/gpt-5.6-sol | 5.00 | 507 | $0.002535 | **assumed encoding** |

### The finding: **normalization changed no ranking, in any stratum**

```
ranking_changed_by_normalization:
  code_python         false
  code_typescript     false
  prose_documentation false
  structured_json     false
  mixed_repo_context  false
```

**Effective token multipliers among currently-priced models span only
1.00–1.11×** — far below RQ-01's headline 1.33×. Meanwhile posted prices span
**263×** (0.019 → 5.00). Token differences are swamped.

### This materially over-states RQ-01's conclusion, and we are correcting it

RQ-01 reported a 1.33× cross-vendor spread and concluded per-token prices are
"not comparable without normalization." That 1.33× was **driven by
Mistral-7B-Instruct-v0.3**, an older tokenizer generation that is *not* the
tokenizer of any model in the current price list.

Among the models a reader would actually be choosing between today, the spread is
**1.03–1.11×**.

**Corrected rule, now evidence-based:**

> Tokenizer normalization changes a cost ranking only when posted prices differ
> by **less than ~11%**. Where price differences exceed that, normalization
> refines the magnitude but does not alter the decision.

That is a *more useful* rule than "prices are incomparable", and it is narrower
than what M4 published. RQ-01's measurement stands; its **interpretation was too
broad**.

### Residual blockers, precisely identified

The comparison is not fully complete. What prevents it:

| Missing information | Consequence |
|---|---|
| **Anthropic offline tokenizer** | Cannot enter any normalized comparison |
| **Google offline tokenizer** | Cannot enter any normalized comparison |
| **OpenAI per-model encoding documentation** | `o200k_base` is an *assumption*; OpenAI rows are provisional |
| `mistralai/Mistral-Small-3.2-24B` tokenizer (HTTP 404) | One priced model unmeasurable — likely a different tokenizer packaging format |

**The two largest closed-weight vendors remain outside every normalized
comparison.** That is unchanged and is now the sole remaining blocker to a
complete cross-vendor cost table.

### Deliverables

| | |
|---|---|
| **Recommendation impact** | Cross-vendor cost comparison **UNBLOCKED for open-weight models with exact tokenizer matches**. Still blocked for Anthropic and Google. The ~11% decision rule is directly implementable. |
| **Schema impact** | Confirms S2's necessity — `tokenizer_verified: false` is the correct state for the OpenAI rows. |
| **Engine impact** | E2 (cross-vendor block) **relaxed to conditional**: permitted where both models have `tokenizer_verified: true`; blocked otherwise. E3 (content-specific multipliers) retained but downgraded in importance — the effect is real and small. |
| **New RQs** | **RQ-01g** — does OpenAI document per-model encodings anywhere? **RQ-01h** — Mistral tokenizer packaging (`mistral-common`/tekken) as an access path. **RQ-01i** — at what price-difference threshold does normalization flip a ranking, formally derived rather than estimated at ~11%? |
| **Prior conclusions** | **PARTIALLY INVALIDATED.** RQ-01's measurement valid; its generalization to "prices are not comparable" was too strong and is corrected. |

## Decision Gate

### **Answer: 2 — Yes, with known limitations.**

The Atlas is ready for broad evidence population, provided the following are
carried as explicit, rendered limitations rather than resolved silently.

**Why not "Yes":**

| Limitation | Recommendation-level impact |
|---|---|
| Anthropic and Google cannot enter normalized cross-vendor cost comparisons | **Real but bounded.** Their per-token prices are publishable and comparable *within vendor*; only cross-vendor normalized cost is blocked. The engine already refuses correctly. |
| Subscription vs metered is not computable in principle | **Real, and answered.** The Atlas gives a substantive negative answer rather than a gap. |
| All usage profiles remain `assumed` | **The largest live limitation.** Every absolute cost figure inherits it. Mitigated: profiles carry stated assumptions and low confidence, and the engine refuses budget queries rather than computing from them. |
| Source capture lacks hashing and archival | Real. Silent vendor edits undetected; calendar re-verification only. |
| Zero Class B and Class C evidence | **Blocks scoring, not population.** No dimension can be scored, so no recommendation can be *made* — but entities can be correctly *populated*. |

**Why not "No":** none of the above prevents adding correct, well-sourced
entities. Each is representable in the current schema, each is surfaced to the
reader by machinery already built, and none requires redesign. The two blockers
that could have forced a redesign — the context discrepancy and the tokenizer
correction — were resolved, and the second *narrowed* our claims rather than
breaking the model.

**Conditions attached to resuming:**

1. Entities populated with `tokenizer_verified: false` unless empirically
   established.
2. No cross-vendor cost claim involving Anthropic or Google.
3. No dimension scored until Class B/C evidence exists — population and scoring
   proceed as separate phases.
4. RQ-01's over-broad conclusion corrected in the published report before it is
   cited internally.

**The honest summary:** four blockers, one confirmed and strengthened, one
invalidated (ours), one implemented cleanly, one achieved with a null result that
made our previous claim smaller and more accurate. Two of the four made the Atlas
*less* confident than it was yesterday, which is the correct direction of travel
for a research program that is working.
