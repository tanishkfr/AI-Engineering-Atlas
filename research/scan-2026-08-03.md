## Findings that changed the design

### F1 — A tree cannot hold this ecosystem
Multiple major entities occupy 3–4 layers simultaneously (a vendor CLI that is
also a subscription, an SDK, and a hosted runner; an editor that is also a model
vendor and a review tool). → Taxonomy rebuilt as **faceted**, not hierarchical.

### F2 — Identity is unstable
At least one prominent project renamed twice in twelve months. Multiple
acquisitions absorbed tools into competitors. A major protocol changed
governance from a vendor to a foundation. → **Synthetic permanent IDs, mandatory
aliases, lifecycle relations.**

### F3 — Nine categories missing from the original brief
Code review agents · orchestration and parallel runners · code intelligence /
retrieval · observability and eval platforms · app builders · skills and
extension registries · standards and protocols as entities · governance bodies ·
security research on the agent ecosystem. → All added as first-class.

### F4 — Benchmark figures are not comparable, and this is the norm
Six different SWE-bench Verified figures surfaced in a single scan session
(roughly 80.6 / 80.8 / 85.5 / 87.6 / 93.4 / 95.0), attributed to different
subjects, harnesses, variants (Verified vs Pro vs Live), dates, and operators —
some vendor-reported, some independent, presented interchangeably by aggregators.

This is the single strongest validation of the framework's design. It
independently justifies: the model/version/**endpoint** split (TAXONOMY §2 L1),
the `via` requirement on M-type claims (SCHEMA §5), the benchmark-vs-leaderboard
entity split (TAXONOMY §3 M1), and the "never place incomparable numbers in the
same column" rule (INFORMATION-ARCHITECTURE §2.3).

→ Becomes the first decision page written in Milestone 2:
*"Why do benchmark scores for the same model disagree, and which should you
believe?"*

### F5 — The adoption/trust gap is the ecosystem's central unanswered question
Scan sources converge on: very high adoption, *falling* trust in output, and
review time now reportedly exceeding writing time, with self-reported
productivity plateauing after an initial jump.

If even approximately true, this reframes the entire Atlas. The interesting
question stops being "which tool is best" and becomes "does this help, under what
conditions, and what does it cost in review burden." → Elevated to a top-level
question in the index with answer state `contested`. **Requires Class B sources
before anything is published** — this is precisely the kind of striking claim
that aggregation distorts.

## Entity inventory

Placement only. `†` = named in scan but existence/nature not independently
confirmed; treat with extra suspicion.

### L1 — Model
Frontier closed-weight families from the major labs (multiple active versions
and preview lines per family, several released since May 2026 †) · open-weight
coding families from Chinese labs (several with claimed frontier-adjacent coding
performance) · open-weight Western families · code-specialized fine-tunes ·
locally-runnable quantized variants.

*Scan note:* naming is churning fast — families now ship named sub-variants and
preview lines that are easy to mistake for versions. The family/version/endpoint
split handles this; a flat "model" record would not.

### L2 — Access
First-party vendor APIs · multi-model aggregators/routers · serverless per-token
providers (a consolidated set of roughly seven majors) · speed-specialist
hardware providers · per-GPU-second platforms · subscription tiers across every
major vendor · free tiers · BYOK arrangements.

*Scan note:* a wide price spread on identical open weights across providers was
repeatedly asserted. If verified, this is one of the highest-value facts the
Atlas can carry — and it is invisible in every model-centric comparison.

### L3 — Harness
CLI agents (vendor-first and model-agnostic open-source) · IDE-resident agents ·
background/cloud agents doing issue-to-PR work · always-on personal agents
reached through messaging · app builders · agent SDKs from multiple vendors.

*Scan note:* the always-on personal-agent category grew from near-nothing and
carries a distinct security profile. It did not exist in the original brief.

### L4 — Surface
AI-first editor forks · extensions for established IDEs · terminal · web
consoles · code-host/PR integrations · messaging platforms as agent surfaces ·
mobile.

### L5 — Interop
The dominant tool protocol (now under foundation governance) and its server
ecosystem · a cross-vendor packaged-instruction standard with published spec ·
repo-level instruction-file conventions · plugin and hook systems · multiple
competing registries indexing servers and skills at very large scale.

*Scan note:* registries report catalog sizes in the tens of thousands to
millions, while independent audits report low average quality and prompt
injection in a substantial fraction of sampled artifacts. **Registry size is an
anti-signal as often as a signal.** Directly motivated EVALUATION.md D13.

### L6 — Context
Code intelligence / index-and-graph platforms · retrieval systems · memory
layers · context-format conventions · compaction strategies.

*Scan note:* live architectural split between **index-first** and **agentic
search**. Modelled as a `context_strategy` facet.

### L7 — Orchestration
Agent frameworks in three rough families (graph-based, role-based, SDK-native) ·
parallel runners · **git-worktree isolation tooling** · schedulers · fleet
managers.

*Scan note:* worktree isolation became load-bearing during 2026 — a whole tool
cluster exists solely so parallel agents stop overwriting each other. Strongest
argument for L7 as its own layer.

### L8 — Assurance
Code review agents (several, consolidating rapidly through acquisition) · static
analysis and SAST vendors moving into AI review · test generation · security
scanners · eval platforms · LLM/agent observability · CI gates.

*Scan note:* the most acquisition-heavy layer in the scan → highest aggregate
continuity risk (D12), and worth saying so explicitly on every page here.

### L9 — Practice
Spec-driven development (with a large open-source toolkit and vendor
implementations) · context engineering as a named discipline · prompt
engineering · review workflows for AI-generated code · parallel-agent workflows ·
anti-patterns.

### M1 — Evidence artifacts
Repository-patching benchmarks and their variants · terminal/CLI benchmarks ·
polyglot editing benchmarks · frontend arenas · agentic indices · long-horizon
software-evolution benchmarks · multiple independent leaderboards publishing
divergent numbers for nominally identical benchmarks · large annual developer
surveys · vendor and research-lab reports · academic work on harness engineering

### M2 — Institutions
Frontier labs · open-weight labs · editor and tooling vendors · cloud and
hyperscaler platforms · the foundation now governing the dominant tool protocol ·
registry operators · security research groups auditing the extension ecosystem.

## Coverage gaps in the scan itself

Recorded so the next scan is better, not so this one looks complete.

1. **Non-English sources absent.** Significant open-weight model discussion
   happens on platforms the scan did not touch. A known, uncorrected bias
   (METHODOLOGY §9).
2. **No primary sources retrieved.** By design for a scan; means zero
   verification depth.
3. **Enterprise reality under-sampled.** Nearly all sources address individual
   and small-team use.
4. **Cost data entirely unverified.** Every price seen was secondary.
5. **Failure and abandonment under-sampled.** The scan queried categories, not
   negatives. Milestone 2 must run the explicit negative-case searches from
   METHODOLOGY §3.
6. **Security research touched only glancingly** despite surfacing findings
   serious enough to change the rubric. Deserves its own dedicated scan.
7. **Local/self-hosted inference economics** are asserted everywhere and
   measured nowhere in the scan. Strong Class D experiment candidate.
